# 原生家庭板块：程序流程中发给 AI 的提示词一览

以下按**原生家庭**板块从「进入 → 对话提交 → 创建小结」的流程，列出每次调用 AI 时**实际发送的消息顺序**。用户内容可固定不写，重点看**小结那一步的 system 到底是什么**，便于排查为何未返回 JSON。

---

## 一、流程与消息顺序（按 API 发送顺序）

### 第一次「提交会话」（用户发一条后点提交）

接口：`POST /api/c/sessions/{sessionId}/submit` → `InterviewSessionService.submit` → `getInterviewPrompts("FAMILY_ORIGIN", GROOM)` → `chatWithHistory(systemPrompt, history)`。

发往 AI 的 `messages` 顺序为：

| 序号 | 角色 | 说明 | 内容来源 |
|------|------|------|----------|
| **0** | **system** | 访谈系统提示词 | 场景 `BOARD_INTERVIEW_FAMILY_ORIGIN_GROOM` 下全部 prompt 的 `content` 用 `\n\n` 拼接。顺序：`FAMILY_ORIGIN_SYSTEM`（PREPEND）+ `FAMILY_ORIGIN_QUESTIONS`（APPEND）。即：**DB 中 code=FAMILY_ORIGIN_SYSTEM 的 content** + `\n\n` + **DB 中 code=FAMILY_ORIGIN_QUESTIONS 的 content**。 |
| 1 | user | 用户内容 | 会话中第一条消息（多为欢迎语后的用户首条）。可固定写「用户第一条消息」等占位。 |
| 2 | assistant | AI 回复 | 上一条 user 的回复（欢迎语等）。 |
| 3 | user | 用户内容 | 会话中第二条用户消息。可占位。 |
| … | … | 交替 user/assistant | 直至当前会话全部历史。 |

说明：**0** 是整次请求里唯一的 system；**1、2、3、…** 来自 `messageRepository.findBySessionIdOrderBySequenceNoAsc`，按顺序转为 user/assistant。

---

### 创建小结（点击生成小结）

接口：`POST /api/c/sessions/{sessionId}/summaries` → `BoardSummaryService.createSummary` → `getSummaryPrompts("FAMILY_ORIGIN")` → `aiChatService.generateSummary(prompt, conversation, boardName)` → `chat(prompt, List.of(userContent))`。

发往 AI 的 `messages` 顺序为：

| 序号 | 角色 | 说明 | 内容来源 |
|------|------|------|----------|
| **5** | **system** | **小结提示词（本条即「发给 AI 的小结提示词」完整内容）** | 见下方 **二、小结 system 的完整拼接**。 |
| 6 | user | 小结时的用户消息 | 见下方 **三、小结 user 内容**。 |

---

## 二、小结 system 的完整拼接（即「5. 小结提示词」到底是什么）

`getSummaryPrompts("FAMILY_ORIGIN")` 逻辑：

- 场景码：`BOARD_SUMMARY_FAMILY_ORIGIN`。
- 该场景下所有 prompt 的 `content` 按 `display_order` 用 **`\n\n`** 拼接。
- **过滤**：去掉 `promptCode` 以 **`_SYSTEM`** 结尾的项（访谈系统角色不参与小结）。

因此参与拼接的是：**FAMILY_ORIGIN_QUESTIONS**（code 不以 _SYSTEM 结尾）+ **BOARD_SUMMARY_COMMON_PROMPT**。

当前库里若 `BOARD_SUMMARY_FAMILY_ORIGIN` 绑定了：

- `FAMILY_ORIGIN_SYSTEM` → 被过滤，不参与。
- `FAMILY_ORIGIN_QUESTIONS` → 参与。
- `BOARD_SUMMARY_COMMON_PROMPT` → 参与。

则 **发给 AI 的小结 system = 下面 (A) + `\n\n` + (B)**。

### (A) FAMILY_ORIGIN_QUESTIONS 的 content（DB，可能随版本不同）

V14 中的示例为：

```text
请针对「原生家庭」主题生成 5～8 个开放式问题，例如：成长中谁对你影响最大、家里有什么传统、父母如何相处等。问题要具体、易于回答。
```

若你库中该条被其它迁移或后台改过，以实际 DB 为准。

### (B) BOARD_SUMMARY_COMMON_PROMPT 的 content（执行 V24 后）

即「只输出 JSON、禁止叙述」的那条，**完整内容**如下（与 V24 中一致）：

```text
【角色设定】
你是"数字爸爸"系统的首席数据结构化提炼官。你的任务是对用户在采访阶段产生的口语化聊天记录进行深度脱水，并严格按照产品 UI 规范，将其整理为一份"可供用户阅读、勾选和确认"的结构化摘要卡片数据。
【核心提炼纪律（防编造与防失控红线）】
1. 绝对忠实原意： 没有明确依据的内容，绝不能脑补成具体事实。遇到模糊指代，尽量保留原话的表述边界。
2. 文本极简原则： 提取的条目必须"短、清楚、可判断对错"，拒绝长篇大论，拒绝抽象的空话。每条原则上不超过 30 个字，方便用户在手机端一眼看懂并作出确认。
3. 严格的属性分类： 提取的核心要点必须明确区分【事实类】（时间/人物/经历/事件/关系）和【表达类】（态度/金句/价值观/情绪高光）。
【输入数据】
当前对话模块：[传入当前维度，如：原生家庭 / 爱情故事]
原始对话记录：
[插入多轮对话文本]
【输出数据结构（严格输出 JSON 格式）】
请深度分析对话记录，且只输出一份合法的 JSON，不要输出任何 markdown 标记（如 ```json）或前后说明文字，不要输出任何中文叙述、旁白或括号说明，以便后端直接解析。你必须直接以 { 开头、以 } 结尾，仅输出下述结构：
{
  "title": "对话小结",
  "key_characters": [
    { "name": "人物称呼或姓名", "role_label": "关系或角色标签" }
  ],
  "core_points": [
    { "type": "事实类", "content": "提取的具体要点文本" },
    { "type": "表达类", "content": "提取的具体要点文本" }
  ],
  "more_details": ["细节条目1", "细节条目2"],
  "storage_dimension": "当前对话模块名称"
}
【JSON 字段生成强制规则】
1. title (标题)：固定输出"对话小结"或结合模块输出（如"爱情故事小结"）。
2. key_characters (关键人物)：数组，每项为对象，且仅包含 name、role_label 两个字段；最多提取 3 个；若无则输出 []。
3. core_points (核心要点)：最少 3 条，最多 8 条；type 仅允许 "事实类" 或 "表达类"；content 客观极简，单条原则上不超过 30 字。
4. more_details (更多细节)：次要信息放此数组；无则输出 []。
5. storage_dimension (存储维度)：直接填入本次输入的"当前对话模块"名称。
```
因此：**程序里「5. 小结提示词」= (A) + 两个换行 + (B)**。若 (A) 是「生成 5～8 个开放式问题」，模型可能被带偏去生成问题或叙述而非 JSON；可考虑让小结场景**仅绑定 BOARD_SUMMARY_COMMON_PROMPT**（不绑 FAMILY_ORIGIN_QUESTIONS），或在 DB 中把小结用的 QUESTIONS 改成与 JSON 输出一致的说明。

## 三、小结时的用户内容（可固定不写）

`DeepSeekAiChatService.generateSummary` 中构造的**一条 user 消息**为：

```text
请根据以下采访对话生成板块小结，板块名称：「原生家庭」。

对话内容：
用户：（此处为会话中第一条用户消息内容）
AI：（此处为第一条 AI 回复）
用户：（第二条用户消息）
AI：（第二条 AI 回复）
…
```

即：固定前缀 **`请根据以下采访对话生成板块小结，板块名称：「` + boardName + `」。\n\n对话内容：\n`** + `conversation`。`conversation` 来自 `BoardSummaryService`：同 session 下所有消息按 `sequence_no` 排序，每行 `"用户："` 或 `"AI："` + 该条 `content`，行间 `\n`。

---

## 四、汇总：为什么可能不是 JSON

1. **小结 system 前面多了 (A)**：若 (A) 是「生成 5～8 个开放式问题」，模型会先看到「提问」任务，容易输出问题列表或叙述，而不是纯 JSON。
2. **只保留 (B) 更稳**：确认小结场景 `BOARD_SUMMARY_FAMILY_ORIGIN` 在过滤 _SYSTEM 后**只**包含 `BOARD_SUMMARY_COMMON_PROMPT`（不包含 FAMILY_ORIGIN_QUESTIONS），则发给 AI 的「5. 小结提示词」就是上面 (B) 的全文，更利于只输出 JSON。

建议在管理端或库里查 `prompt_scene_item` 中 `scene_id` = BOARD_SUMMARY_FAMILY_ORIGIN 的 `prompt_code` 列表，确认是否包含 QUESTIONS；若包含且希望小结必出 JSON，可去掉该绑定或改为仅小结用说明文案。
